# AGENTS.md

## Layout
- Nix flake monorepo of BlueForest theme ports. `modules/<app>/` is a self-contained flake; its `flake-module.nix` is both imported by the app flake and published as `flakeModules.default` for the root `flake.nix` to compose.
- Implemented apps: `modules/vscode` (VS Code/VSCodium extension), `modules/bat` (TextMate theme), `modules/neovim` (Neovim colourscheme and lualine theme), `modules/starship` (Starship preset), `modules/opencode` (OpenCode theme), and `modules/sbt` (sbt prompt).
- The VS Code extension is theme-only: `package.json` has no `main`, and there is no JS to build, test, or lint. Node and `vsce` are only for packaging.
- Theme files are hand-edited sources, not generated: `modules/vscode/themes/Blueforest-color-theme.json`, `modules/bat/themes/BlueForest.tmTheme`, `modules/neovim/themes/blueforest.lua`, `modules/neovim/themes/lualine-blueforest.lua`, `modules/starship/themes/blueforest.toml`, and `modules/opencode/themes/blueforest.json`. Checks compare packaged copies against them. `modules/sbt` is the exception: it does not define a theme, it installs the upstream `sbt-prompt` plugin and selects its `BlueforestTheme` from `modules/sbt/config/`.
- The CI workflows are the opposite: they are generated. `workflows/` holds their definitions in Nix, and `.github/workflows/*.yml` is rendered from them by `actions-nix`. Never edit the rendered files by hand; edit the definitions and render again.
- `README.md` is a short entry point. The consumer-facing contract (installation, outputs, identifiers, per-app behaviour) is the documentation site: `mkdocs.yml` at the root, and the Markdown files under `docs/`. Update the docs when outputs or module behavior change, and keep the READMEs pointing at them.
- `docs/` is the MkDocs site: `docs/index.md`, `docs/installation.md`, `docs/themes/`, `docs/reference/`, `docs/hacking/`, and `docs/license.md`. User-facing material lives outside `docs/hacking/`; repository structure and contribution material live under it.

## Verify
- Format: `nix fmt` (nixfmt, taplo, prettier for `*.json`, stylua for `*.lua`, shfmt with tabs, shellcheck).
- Fast checks: `nix flake check` at the root (includes `treefmt`). Per app: `nix flake check ./modules/vscode`, `nix flake check ./modules/bat`, `nix flake check ./modules/neovim`, `nix flake check ./modules/starship`, `nix flake check ./modules/opencode`, `nix flake check ./modules/sbt`. CI runs all seven.
- Two checks build an editor and are only run on purpose: `BLUEFOREST_VSCODE_INTEGRATION_CHECK=1` (VSCodium) and `BLUEFOREST_NEOVIM_NIXVIM_CHECK=1` (nixvim). Both need `--impure`, because they read the environment. The CI sets both, so they run there. `nix build .#vscode-integration-check` and `nix build .#neovim-nixvim-check` build them on their own.
- Single check: `nix build .#checks.x86_64-linux.<name>`, where `<name>` is `version`, `overlay`, `treefmt`, `documentation`, `workflows`, `workflows-lint`, `vscode-extension`, `vscode-configuration`, `bat-theme`, `bat-theme-home`, `bat-theme-nixos`, `neovim-theme`, `neovim-configuration`, `neovim-module`, `starship-preset`, `starship-render`, `starship-wrapper`, `starship-module`, `opencode-theme`, `opencode-configuration`, `opencode-module`, `sbt-package`, or `sbt-module`.
- Documentation: `nix build .#documentation` builds the site, and `nix run .#watch-documentation` serves it with live reload. The root `documentation` check builds it with `--strict`, so broken internal links and pages missing from the nav fail `nix flake check`.
- The `workflows` check renders the workflows into a scratch directory and compares them with the committed ones. It fails when the rendered files are not the committed ones. It is skipped when `BLUEFOREST_SKIP_WORKFLOWS_CHECK=1`, which the CI does on a pull request, where the workflow of the CI renders the files and commits them to the branch.
- The `workflows-lint` check renders the workflows into a scratch directory and runs `actionlint` over the result. It does not depend on what is committed, so it runs on every pull request.
- The VSCodium integration check is intentionally absent from `nix flake check`. Run `BLUEFOREST_VSCODE_INTEGRATION_CHECK=1 nix flake check --impure` or `nix build .#vscode-integration-check` (expensive).
- The root flake owns the pin of nixvim (`inputs.nixvim`), and the application follows it (`inputs.neovim.inputs.nixvim.follows = "nixvim"`). The application keeps a pin of its own in `modules/neovim/flake.lock`, for the consumers that take it on its own. `nix flake lock` does not re-resolve the inputs of a path input: use `nix flake update neovim` after adding a `follows` to it.
- Root flake evaluation only sees tracked files. `git add` new files before running `nix flake check` or `nix build .#...`.
- Shells: one shell for the repository, `nix develop` (the tools of every application, the release tooling and `nixfmt`). There is no shell per application: the definition is the `devshell.toml` of the root, and the module of the root declares it with the `devshell` flake.

## Updates
- Every flake of the repository has a lock file of its own: the root one, and one per application. `update` from `nix develop` (or `tools/update.sh`) updates all of them: the root first, then each application.
- The root owns the pins, so the helper pins the inputs an application shares with the root to the revisions the root resolved, with `nix flake lock --override-input`. Without that step the two drift apart, because the root and the application resolve the branch on their own.
- Dependabot watches the lock files (`.github/dependabot.yml`): the `nix` ecosystem for the root and `/modules/*`, weekly. The `nix` entries are grouped by `dependency-name`, so one pull request carries every lock file that shares the input.
- The versions of the actions of the workflows are updated by Renovate, not by Dependabot: `renovate.json5` has a custom manager that reads them from `workflows/lib.nix`. Dependabot's `github-actions` ecosystem cannot do it, because it only reads workflow files, which are generated.
- The version of the sbt prompt plugin is updated by the second custom manager of `renovate.json5`, which reads the tags of the upstream repository. The version is in three places: the declaration of the plugin, the check that pins it, and `docs/themes/sbt.md`. The manager covers the three, so they move together; do not take the version out of the check, or the pin it holds is lost.
- Renovate is the hosted application, so it brings its own credential and the repository holds no secret for it. It cannot run commands either: the commands of the post-upgrade tasks are blocked on the hosted application, so the workflow of the CI renders the workflows for its pull requests and commits them to the branch. Do not add a workflow that runs Renovate: two of them would fight over the same dependency.
- Dependabot runs `nix flake lock --override-input` itself, so it keeps the `original` of an input: a pinned revision does not become permanent.

## Versions and releases
- The version comes from the tags of the repository, and there is no version file: a release is a tag of the form `vMAJOR.MINOR.PATCH`. `tools/version.sh` derives the version of a commit from the tags: the tag of the commit when it carries one, the latest release before it with the hash of the commit appended otherwise, and `0.0.0` with the hash when there is no tag at all. A tree that is not clean carries a `.dirty` suffix.
- The packages of the repository are never a release: they carry the revision of the commit they are built from (`0.0.0+<revision>`), and the version is computed from `self` in the `flake-module.nix` of every application. Pure Nix cannot read the tags of a repository, so it never claims to know the version of a release.
- The overlays take no version: they are declared in the `flake-module.nix` of the application, where the version is in scope, and they keep the `final: prev:` shape. The modules that publish an overlay (Home Manager, NixOS and nixvim) receive the overlay as a value, so that there is only one overlay per application.
- `modules/vscode/package.json` carries the placeholder `0.0.0`: the manifest is patched with the version of the package before the extension is packaged, and the release workflow patches it with the version of the release.
- Prefer the helper over hand-editing: `release` from `nix develop`, or `nix run .#release`. It is interactive, needs authenticated `gh` and network, and it pushes; do not run it unattended. It asks for the version, checks it against the releases of GitHub, stamps the changelogs, commits, tags and pushes.
- The helper releases the whole repository: there is no script per application, and the release is one tag, one version and one GitHub release with the assets of every application. An application that is not released yet does not get an asset of its own.
- Changelogs: `modules/<app>/CHANGELOG.md`, newest section first, heading `## X.Y.Z - [DD-MM-YYYY]`. A changelog that has changes that are not released yet carries an `Unreleased` section, which the release turns into the section of the release. The root `CHANGELOG.md` links to the app changelogs and has an `Unreleased` section as well.
- Release workflow: `.github/workflows/release.yml` runs on the push of a tag `v*` and releases every application unconditionally. Its definition is `workflows/release.nix`. The job `create-release` creates the GitHub release with the changelog of the version, and every application uploads its asset to that release afterwards, so that the release is never created twice; the job `publish-release` publishes it when every application is done, and the job `docs` calls the documentation workflow as the last step.
- Documentation workflow: `.github/workflows/docs.yml` is rendered from `workflows/docs.nix`. It builds `packages.documentation` with `nix build .#documentation`, uploads it with `actions/upload-pages-artifact`, and deploys it with `actions/deploy-pages`. It runs on pushes to `master`, on manual dispatch, and on `workflow_call` from the release. The repository must have GitHub Pages configured with GitHub Actions as its source; the site is published at <https://alonsodomin.github.io/blueforest-theme/>.

## Conventions and traps
- Split licence: `modules/*/themes/**`, images, `*.md`, and `docs/**` are CC BY 4.0; Nix, scripts, workflows, `mkdocs.yml`, and manifests are MPL-2.0. New code/config files start with `# SPDX-License-Identifier: MPL-2.0`. `NOTICE.md` maps paths.
- Shell is bash and uses tabs (`treefmt.nix`: shfmt `indent_size = 0`; shfmt simplifies the code it formats, which is its default); shellcheck must pass.
- Identifiers: theme ID `BlueForest`; extension ID `alonsodomin.blueforest-theme`; nixpkgs attr `blueforest-vscode-theme`; bat theme name `BlueForest`; Neovim package `blueforest-neovim-theme`; Neovim colourscheme name `blueforest`; lualine theme name `blueforest`; Starship preset name `blueforest`; Starship packages `blueforest-starship-preset` and `blueforest-starship`; OpenCode theme name `blueforest`; OpenCode package `blueforest-opencode-theme`; sbt package `blueforest-sbt-prompt`; sbt theme `BlueforestTheme` from the upstream `sbt-prompt` plugin. Note the lowercase `f` in `Blueforest-color-theme.json`.
- The VS Code module is defined once, in `modules/vscode/nix/modules/default.nix`, which takes the overlay of the application as an argument. The flake module imports it for `homeModules.vscode`, and the `vscode-configuration` check evaluates it again.
- The VSIX build uses `vsce package --no-dependencies`; `.vscodeignore` decides what ships. Keep dev files out and add new runtime files explicitly. `*.vsix` is git-ignored.
- `.vscode/launch.json` still points at the old `vscode/` path; don't rely on F5. Use `code --extensionDevelopmentPath=$PWD/modules/vscode` or package the VSIX.
- The module of an application (`modules/<app>/flake-module.nix`) is a function of the inputs of that application: the flake of the application binds them with `flake-parts-lib.importApply` and publishes the module as `flake.flakeModules.default`. The arguments of the module are the ones of the flake that imports it, so `inputs` is the input set of the consumer and the packages are built with the nixpkgs of the consumer; the checks use `appInputs`, the inputs of the application. A consumer that imports the module needs no `devshell`, `home-manager` or `nixvim` input of its own.
- `flake.homeModules` is only a declared option once the flake module of Home Manager is imported. The module of an application imports it, preferring the Home Manager of the consumer when it has one (`inputs.home-manager or appInputs.home-manager`), so that the option is declared once and never twice.
- Root aggregate modules are explicit: `flake.nix` currently composes the VS Code, Starship, OpenCode, sbt, and Neovim overlay/modules in `overlays.default` and `homeModules.default`; bat ships packages, an overlay, and checks only (no modules), and sbt has no NixOS module because sbt has no system-wide configuration directory.
- The Neovim package is a plugin (`vimUtils.buildVimPlugin`), so that the colourscheme is at `colors/blueforest.lua` and the theme of lualine at `lua/lualine/themes/blueforest.lua`, which are the two places Neovim and lualine read them from. The plugin directory of the runtimepath is named after the `pname`, not after the store path of the derivation.
- The Neovim module adds the theme to `programs.neovim.plugins` with `lib.mkDefault`, and does not select the colourscheme: Home Manager drops `extraConfig` when the consumer sets `initLua`, so the selection belongs to the consumer's own configuration (`vim.cmd.colorscheme("blueforest")`).
- The nixvim module (`modules/neovim/nix/nixvim.nix`) is imported *into* the configuration of nixvim (`programs.nixvim.imports`), not into the configuration of the system: nixvim builds an instance of nixpkgs of its own, so it has to add the overlay of the theme itself. It only uses three option names of nixvim (`nixpkgs.overlays`, `extraPlugins`, `colorscheme`), so it does not depend on the version of nixvim; only the check does.
- lualine finds the theme of the statusline on its own: its `auto` theme looks the theme up by the name of the colourscheme, and both are `blueforest`. Only the sections of the statusline are configuration.
- The theme of Neovim defines the seven `RainbowDelimiter*` groups, because the rainbow-delimiters plugin reads their colours from the colourscheme. A group the theme does not define leaves the rainbow without a colour.
- The OpenCode module needs `programs.opencode.cli`, which Home Manager gained in commit `6d9655f764`; the `home-manager` input of the root flake is pinned to a revision that has it.
- The OpenCode module does not enable OpenCode: Home Manager writes the theme and the settings of the terminal only when the program is enabled, so the consumer decides.
- Home Manager's `programs.opencode.themes` only takes a path, never a store path string: give it a path literal, or the theme is taken for a JSON object and regenerated.
- OpenCode ignores a theme it cannot read, and it ignores it silently: a missing token or a colour that does not resolve makes it fall back to the theme it ships with. The checks of the application stand in for it, because a TUI cannot be rendered in a build.
- The root `overlays.default` composes with `lib.composeManyExtensions`, not by hand: an overlay takes `final` and `prev`, and folding them by hand loses one of the two. `tests/overlay.nix` guards the result.
- The workflows are rendered by `actions-nix`, whose module is imported into the root flake. `flake.actions-nix.workflows` is a top-level option, not a per-system one: `perSystem.<system>.flake` is not an option. Render with `nix run .#render-workflows`, and commit the result; the pre-commit hook of the development shell does it for you.
- The rendered files carry the header that `actions-nix` writes, and PyYAML folds the long expressions at eighty columns: the value of a folded scalar is the same, but the file reads differently from a hand-written one.
- An expression of GitHub is written `\${{ ... }}` in a double-quoted string of Nix, and `''${{ ... }}` in an indented one. The second is easy to miss, and the file does not evaluate without it.
- `actionlint` is part of the check of the workflows, and it is strict: the inputs of a reusable workflow go under `on.workflow_call.inputs`, a job that reads the output of another job uses `needs.<job>.outputs.<name>` and not `steps.<id>.outputs.<name>`, and the `schedule` trigger takes a mapping (`{ cron = "..."; }`) and not a bare string.
- An explicit `if` on a job replaces the implicit one, which skips the job when a job it needs did not succeed. Every job of the release workflow that carries a condition therefore states the result of the jobs it needs. The release workflow has no condition on the applications: a tag releases all of them.
- `RENOVATE_ALLOWED_COMMANDS` is a global option of Renovate, so it comes from the environment and not from `renovate.json5`. The hosted application does not run commands at all, so the option is not used here.
- The READMEs are short entry points, not installation manuals: the root `README.md` links to the doc site, and every `modules/<app>/README.md` links to its page under `docs/themes/`. Do not put installation steps, output tables, or repository structure back into them.
- The docs use `mkdocs-material` with `font: false`, so the build stays hermetic. Do not add a plugin that downloads assets at build time. Links from `docs/` to repository files outside `docs/` use absolute GitHub URLs, not relative paths, because `mkdocs build --strict` validates internal links.
- The documentation site deploys to GitHub Pages from the `docs` workflow. Do not add a second deployment workflow: the release calls the same one.
- The sbt prompt is not defined here: `modules/sbt/config/` only declares `com.github.alonsodomin:sbt-prompt` and selects `BlueforestTheme`. Keep it that way; the prompt and the palette live upstream at <https://github.com/alonsodomin/sbt-prompt>.
- sbt has nothing to publish but its two files: the prompt and its theme are provided by the upstream plugin, so the release of the repository carries them as an asset of their own, in `workflows/release.nix`.
- The sbt Home Manager module is optionless and inert unless `programs.sbt.enable = true`. It writes `~/.sbt/1.0/plugins/sbt-prompt.sbt`, `~/.sbt/1.0/blueforest-prompt.sbt`, `$XDG_CONFIG_HOME/sbt/2/plugins/sbt-prompt.sbt`, and `$XDG_CONFIG_HOME/sbt/2/blueforest-prompt.sbt`. `home.packages = [ pkgs.blueforest-sbt-prompt ]` alone does not install them.
- sbt 1 reads its global base from `~/.sbt/1.0`; sbt 2 uses `$XDG_CONFIG_HOME/sbt/2`. In both, `plugins/` holds plugin declarations and the base itself holds the settings that can use them.

## Adding an application
Mirror `modules/bat` (the simplest app) or `modules/starship` (a package with an overlay and modules): create `flake.nix`, `flake-module.nix`, `CHANGELOG.md`, and the theme. Then register it in root `flake.nix` (path input with `follows` + `inputs.<app>.flakeModule`), expose it in the root aggregate modules if it provides one, add it to the list of applications in `workflows/lib.nix` (the CI matrix) and to the table of `workflows/release.nix` (the release workflow, with the way it is packaged and the asset it uploads), and update `README.md`, `CHANGELOG.md`, and `NOTICE.md`. Add a user-facing page under `docs/themes/`, a nav entry in `mkdocs.yml`, and a row in `docs/themes/index.md` and the root `README.md`. Keep installation snippets in that page in sync with the configuration checks. There is no development shell per application: the tools of an application go into the `devshell.toml` of the root.
