# AGENTS.md

## Layout
- Nix flake monorepo of BlueForest theme ports. `modules/<app>/` is a self-contained flake; its `flake-module.nix` is both imported by the app flake and published as `flakeModules.default` for the root `flake.nix` to compose.
- Implemented apps: `modules/vscode` (VS Code/VSCodium extension), `modules/bat` (TextMate theme), `modules/neovim` (Neovim colourscheme and lualine theme), `modules/starship` (Starship palette and preset), `modules/opencode` (OpenCode theme), `modules/sbt` (sbt prompt), `modules/eza` (eza theme), `modules/zed` (Zed extension), `modules/yazi` (Yazi flavour), `modules/kitty` (kitty theme), `modules/mkdocs` (MkDocs stylesheet), `modules/claude-code` (Claude Code custom theme), `modules/btop` (btop theme), `modules/lazygit` (lazygit theme), `modules/md-tui` (md-tui theme), and `modules/noctalia` (Noctalia palette).
- The VS Code extension is theme-only: `package.json` has no `main`, and there is no JS to build, test, or lint. Node and `vsce` are only for packaging, and the packaging happens in Nix, not in the development shell.
- Theme files are hand-edited sources, not generated: `modules/vscode/themes/Blueforest-color-theme.json`, `modules/vscode/themes/Blueforest-light-color-theme.json`, `modules/bat/themes/BlueForest.tmTheme`, `modules/bat/themes/BlueForestLight.tmTheme`, `modules/neovim/themes/blueforest.lua`, `modules/neovim/themes/blueforest-light.lua`, `modules/neovim/themes/lualine-blueforest.lua`, `modules/neovim/themes/lualine-blueforest-light.lua`, `modules/starship/themes/blueforest.toml`, `modules/starship/themes/palettes/blueforest.toml`, `modules/starship/themes/palettes/blueforest-light.toml`, `modules/opencode/themes/blueforest.json`, `modules/eza/themes/blueforest.yml`, `modules/yazi/themes/blueforest.yazi/flavor.toml`, `modules/yazi/themes/blueforest-light.yazi/flavor.toml`, `modules/kitty/themes/blueforest.conf`, `modules/kitty/themes/blueforest-light.conf`, `modules/mkdocs/themes/blueforest.css`, `modules/claude-code/themes/blueforest.json`, `modules/claude-code/themes/blueforest-light.json`, `modules/btop/themes/blueforest.theme`, `modules/lazygit/themes/blueforest.json`, `modules/md-tui/themes/blueforest.json`, `modules/md-tui/themes/blueforest-light.json`, and `modules/noctalia/themes/blueforest.json`. Checks compare packaged copies against them. Two applications are the exception: `modules/sbt` does not define a theme, it installs the upstream `sbt-prompt` plugin and selects its `BlueforestTheme` from `modules/sbt/config/`, and `modules/zed` takes its theme from the `zed-blueforest-theme` extension, which is a submodule at `modules/zed/extension/`.
- One theme file is generated: `modules/noctalia/themes/blueforest-v2.json` is the format 2 of the community palette registry of Noctalia, and it is rendered from `modules/noctalia/themes/blueforest.json` by `modules/noctalia/themes/format2.jq`. The `noctalia-palette-v2` check renders it again and compares it with the committed one, so the two cannot drift. Edit the canonical file, never the generated one.
- The fixtures of the check of the render of Starship live in `modules/starship/tests/`: `community-palette.toml` and `community-palette-light.toml` are the palettes of the community catalogue of Noctalia for Starship, with the colours of BlueForest, and they are hand-edited like every other source of the repository. They are not shipped: the check of the render uses them to prove that the preset paints with the palette of the catalogue.
- The CI workflows are the opposite: they are generated. `workflows/` holds their definitions in Nix, and `.github/workflows/*.yml` is rendered from them by `actions-nix`. Never edit the rendered files by hand; edit the definitions and render again.
- The changelog of a release is written by CoCoGitto, the conventional commit toolbox of the repository, out of the commits of the release, and it is committed to the repository: the one of the repository at the root, and the one of every application in its own directory. `cog.toml` is the configuration of the tool: the prefix of the tags, the scopes the commits may carry, the template of the changelog, and the applications of the monorepo. The template is the built-in `remote` one, so the entries of the changelog link to the commits and to the authors.
- `README.md` is a short entry point. The consumer-facing contract (installation, outputs, identifiers, per-app behaviour) is the documentation site: `mkdocs.yml` at the root, and the Markdown files under `docs/`. Update the docs when outputs or module behavior change, and keep the READMEs pointing at them.
- `docs/` is the MkDocs site: `docs/index.md`, `docs/installation.md`, `docs/themes/`, `docs/reference/`, `docs/hacking/`, and `docs/license.md`. User-facing material lives outside `docs/hacking/`; repository structure and contribution material live under it.

## Verify
- Format: `nix fmt` (nixfmt, deadnix and statix for Nix, taplo, prettier for JSON, JSON5, YAML and CSS, stylelint for CSS, xmllint for XML and SVG, stylua for `*.lua`, shfmt with tabs, shellcheck).
- Fast checks: `nix flake check "path:."` at the root (includes `treefmt`). Per app: `nix flake check "path:./modules/vscode"`, `nix flake check "path:./modules/bat"`, `nix flake check "path:./modules/neovim"`, `nix flake check "path:./modules/starship"`, `nix flake check "path:./modules/opencode"`, `nix flake check "path:./modules/sbt"`, `nix flake check "path:./modules/eza"`, `nix flake check "path:./modules/zed"`, `nix flake check "path:./modules/yazi"`, `nix flake check "path:./modules/kitty"`, `nix flake check "path:./modules/mkdocs"`, `nix flake check "path:./modules/claude-code"`, `nix flake check "path:./modules/btop"`, `nix flake check "path:./modules/lazygit"`, `nix flake check "path:./modules/md-tui"`, `nix flake check "path:./modules/noctalia"`. CI runs all seventeen.
- The `path:` prefix matters: the checks run against the working tree, and not against the git tree. The extension of Zed is a submodule of the repository, and Nix cannot read the contents of a submodule of a git tree, so the submodule has to be checked out for the checks to see it.
- Two checks build an editor and are only run on purpose: `BLUEFOREST_VSCODE_INTEGRATION_CHECK=1` (VSCodium) and `BLUEFOREST_NEOVIM_NIXVIM_CHECK=1` (nixvim). Both need `--impure`, because they read the environment. The CI sets both, so they run there. `nix build "path:.#vscode-integration-check"` and `nix build "path:.#neovim-nixvim-check"` build them on their own.
- Single check: `nix build "path:.#checks.x86_64-linux.<name>"`, where `<name>` is `version`, `overlay`, `treefmt`, `documentation`, `workflows-validate`, `workflows-lint`, `vscode-extension`, `vscode-configuration`, `vscode-theme`, `bat-theme`, `bat-theme-home`, `bat-theme-nixos`, `bat-render`, `bat-module`, `neovim-theme`, `neovim-configuration`, `neovim-module`, `starship-preset`, `starship-palette`, `starship-render`, `starship-wrapper`, `starship-module`, `opencode-theme`, `opencode-roles`, `opencode-configuration`, `opencode-module`, `sbt-package`, `sbt-module`, `eza-theme`, `eza-render`, `eza-module`, `zed-extension`, `zed-theme`, `zed-module`, `zed-colours`, `fences`, `yazi-theme`, `yazi-render`, `yazi-module`, `yazi-tmtheme`, `yazi-asset`, `kitty-theme`, `kitty-parse`, `kitty-module`, `mkdocs-theme`, `mkdocs-render`, `claude-code-theme`, `claude-code-module`, `btop-theme`, `btop-render`, `btop-module`, `lazygit-theme`, `lazygit-render`, `lazygit-module`, `lazygit-colours`, `md-tui-theme`, `md-tui-render`, `md-tui-module`, `md-tui-colours`, `noctalia-theme`, `noctalia-palette-v2`, `noctalia-render`, `noctalia-module`, `noctalia-colours`, `palette-swatches`, `light-colours`, `cog-packages`, `release-assets`, or `documentation`.
- Documentation: `nix build .#documentation` builds the site, and `nix run .#watch-documentation` serves it with live reload. The root `documentation` check builds it with `--strict`, so broken internal links and pages missing from the nav fail `nix flake check`. The development shell generates and serves the site with `generate-docs`, `serve-docs` and `watch-docs`.
- The `workflows-validate` check renders the workflows into a scratch directory and compares them with the committed ones. It fails when the rendered files are not the committed ones, and it runs on every event. On a pull request the CI renders the files and commits them to the branch, so the check reports the ones that are still out of sync.
- The `workflows-lint` check renders the workflows into a scratch directory and runs `actionlint` over the result. It does not depend on what is committed, so it runs on every pull request.
- The VSCodium integration check is intentionally absent from `nix flake check`. Run `BLUEFOREST_VSCODE_INTEGRATION_CHECK=1 nix flake check --impure "path:."` or `nix build "path:.#vscode-integration-check"` (expensive).
- The root flake owns the pin of nixvim (`inputs.nixvim`), and the application follows it (`inputs.neovim.inputs.nixvim.follows = "nixvim"`). The application keeps a pin of its own in `modules/neovim/flake.lock`, for the consumers that take it on its own. `nix flake lock` does not re-resolve the inputs of a path input: use `nix flake update neovim` after adding a `follows` to it.
- Root flake evaluation sees the working tree, so the changes of the working tree are part of it. `git add` new files before running the checks, so that the tree and the submodule agree with the repository.
- Shells: one shell for the repository, `nix develop` (the tools of every application, the changelog tooling and `nixfmt`). There is no shell per application: the definition is the `devshell.toml` of the root, and the module of the root declares it with the `devshell` flake.
- The `devshell.toml` of the root cannot name a package of another flake, so the root flake adds the mkdocs of the `mkdocs-flake` to the shell of the repository: it is the one that carries the theme of Material for MkDocs, which the site of the repository uses. The plain mkdocs of nixpkgs cannot build the site.
- The commands of the documentation live in `tools/docs.sh`, and the development shell exposes them as `generate-docs`, `serve-docs` and `watch-docs`. The site is written under `$PRJ_DATA_DIR`, which is `.data` by default, and the directory is ignored by git.

## Updates
- Every flake of the repository has a lock file of its own: the root one, and one per application. `update` from `nix develop` (or `tools/update.sh`) updates all of them: the root first, then each application.
- The root owns the pins, so the helper pins the inputs an application shares with the root to the revisions the root resolved, with `nix flake lock --override-input`. Without that step the two drift apart, because the root and the application resolve the branch on their own.
- Dependabot watches the lock files (`.github/dependabot.yml`): the `nix` ecosystem for the root and `/modules/*`, weekly. The `nix` entries are grouped by `dependency-name`, so one pull request carries every lock file that shares the input.
- The versions of the actions of the workflows are updated by Renovate, not by Dependabot: `renovate.json5` has a custom manager that reads them from `workflows/lib.nix`. Dependabot's `github-actions` ecosystem cannot do it, because it only reads workflow files, which are generated.
- The version of the sbt prompt plugin is updated by the second custom manager of `renovate.json5`, which reads the tags of the upstream repository. The version is in three places: the declaration of the plugin, the check that pins it, and `docs/themes/sbt.md`. The manager covers the three, so they move together; do not take the version out of the check, or the pin it holds is lost.
- Renovate is the hosted application, so it brings its own credential and the repository holds no secret for it. It cannot run commands either: the commands of the post-upgrade tasks are blocked on the hosted application, so the workflow of the CI renders the workflows for its pull requests and commits them to the branch. Do not add a workflow that runs Renovate: two of them would fight over the same dependency.
- Dependabot runs `nix flake lock --override-input` itself, so it keeps the `original` of an input: a pinned revision does not become permanent.
- The pull requests of Renovate and Dependabot are merged on their own, when the merge gate of the CI has passed: Renovate marks them for the auto-merge of GitHub itself, and the workflow of `workflows/dependabot.nix` marks the ones of Dependabot, because Dependabot cannot do it. The merge is a squash one, because the rules of the repository do not allow the merge commits that the linear history of the branch forbids. The workflow only marks the pull requests of Dependabot, and it never runs the code of them.

## Versions and releases
- The version comes from the tags of the repository, and there is no version file: a release is a tag of the form `vMAJOR.MINOR.PATCH`. `tools/version.sh` derives the version of a commit from the tags: the tag of the commit when it carries one, the latest release before it with the hash of the commit appended otherwise, and `0.0.0` with the hash when there is no tag at all. A tree that is not clean carries a `.dirty` suffix.
- Every application has a version of its own, which is the version of its own tag, `bat-v0.2.0`, and it is bumped when the application changes. The release workflow reads it with CoCoGitto, so that the asset of an application carries the version of the application and not the version of the repository.
- The packages of the repository are never a release: they carry the revision of the commit they are built from (`0.0.0+<revision>`), and the version is computed from `self` in the `flake-module.nix` of every application. Pure Nix cannot read the tags of a repository, so it never claims to know the version of a release.
- The overlays take no version: they are declared in the `flake-module.nix` of the application, where the version is in scope, and they keep the `final: prev:` shape. The modules that publish an overlay (Home Manager, NixOS and nixvim) receive the overlay as a value, so that there is only one overlay per application.
- `modules/vscode/package.json` carries the placeholder `0.0.0`: the manifest is patched with the version of the package before the extension is packaged, and the release workflow patches it with the version of the release.
- A release is made by the helper: `release` from `nix develop`, or `nix run .#release`. It runs `cog bump --auto`, which computes the version of every application that changed, writes the changelogs, commits them and tags the release, and it pushes the branch and the tags afterwards. The push of the tag of the release triggers the release workflow, which does the rest.
- The tools of the repository live in `tools/`, one directory per tool: `main.sh` is the script and `default.nix` is the Nix wrapper of the tool, when it is a package of the root flake. `tools/release` is the helper of the release, `tools/changelog` shows the changelog of the unreleased changes, and `tools/git-guard` is the `pre-push` hook that stops the push of a tag of a release when the user did not confirm it.
- Changelogs: the changelog of the repository is `CHANGELOG.md`, and the changelog of an application is `modules/<app>/CHANGELOG.md`. They are in the format CoCoGitto writes, and the separator `- - -` is what it looks for when it writes the section of a release into them. The commits follow the conventional commits specification, and the scope of a commit is the id of the application it touches (`bat`, `neovim`, `claude-code`, ...), or `repo` when the commit is not of an application. The scopes are checked by CoCoGitto itself, and the list is in `cog.toml`.
- The changelog of the unreleased changes is shown by `packages.blueforest-changelog`, which is the `changelog` command of the development shell. The CI checks the commit messages of every pull request with `cog check`, so a commit that does not follow the specification never reaches the branch.
- Release workflow: `.github/workflows/release.yml` runs on the push of a tag `v*` and releases every application unconditionally. Its definition is `workflows/release.nix`. The job `conventional` checks that the commits of the release follow the conventional commits specification, with the action of CoCoGitto and the range that starts at the tag of the release before; the job `create-release` creates the GitHub release with the section of the changelog of the repository that belongs to the version, and every application reads its own version with CoCoGitto and uploads its asset to that release afterwards, so that the release is never created twice; the job `publish-release` publishes it when every application is done, and the job `docs` calls the documentation workflow as the last step.
- Release assets: every application is one archive, `blueforest-<app>-theme-<version>.tar.gz`, with the variants of the theme in a directory per variant (`dark` and `light`) and the changelog of the application in `CHANGELOG.txt`. The applications that read their theme from a directory of their own keep that layout (Neovim, Zed, sbt, Yazi), and the extension of VS Code is the exception: its asset is the `.vsix` itself, because that is what the marketplaces take. The definitions of the packaging are in `workflows/assets.nix`, and the archive is built from the `files` of the application, so that the workflow and the checks cannot drift apart.
- Documentation workflow: `.github/workflows/docs.yml` is rendered from `workflows/docs.nix`. It builds `packages.documentation` with `nix build .#documentation`, uploads it with `actions/upload-pages-artifact`, and deploys it with `actions/deploy-pages`. It runs on pushes to `master`, on manual dispatch, and on `workflow_call` from the release. The repository must have GitHub Pages configured with GitHub Actions as its source; the site is published at <https://alonsodomin.github.io/blueforest-theme/>.

## Conventions and traps
- Split licence: `modules/*/themes/**`, images, `*.md`, and `docs/**` are CC BY 4.0; Nix, scripts, workflows, `mkdocs.yml`, and manifests are MPL-2.0. New code/config files start with `# SPDX-License-Identifier: MPL-2.0`. `NOTICE.md` maps paths.
- Shell is bash and uses tabs (`treefmt.nix`: shfmt `indent_size = 0`; shfmt simplifies the code it formats, which is its default); shellcheck must pass.
- A check that pipes the output of `tar` into `grep -q` is racy: `grep -q` exits at the first match and closes the pipe, and GNU tar writes the listing one entry per write, so it fails with `tar: stdout: write error` when it writes the entries that follow the match. Nix ignores `SIGPIPE` in a build, and the shell of nixpkgs sets `pipefail`, so the pipeline fails the check. Use `grep -c` instead, which reads the whole stream and carries the same exit status: zero when the entry is there, and one when it is not.
- The patterns of `treefmt` are compiled without a separator: a star crosses the directories, and a pattern that ends with a slash matches nothing. The excludes of `treefmt.nix` are `modules/zed/extension/*` (the extension of Zed is a repository of its own), `.github/workflows/*` (the workflows are rendered, and the check of the workflows compares the rendering with what is committed), and `docs/assets/stylesheets/blueforest.css` (the stylesheet of the documentation is a symlink to the one of the theme, and the formatters would follow it).
- `deadnix` and `statix` rewrite the Nix sources: `nix fmt` removes the dead code and the code that the lints read as wrong. The lint `repeated_keys` of `statix` is disabled, because the checks of the applications declare the options of Home Manager one by one.
- The `bat` module is the exception to the shape of the other modules: its theme needs no input of the application, so the module only needs the Home Manager of the application.
- Identifiers: theme ID `BlueForest`; extension ID `alonsodomin.blueforest-theme`; nixpkgs attr `blueforest-vscode-theme`; bat theme name `BlueForest`; Neovim package `blueforest-neovim-theme`; Neovim colourscheme name `blueforest`; lualine theme name `blueforest`; Starship preset name `blueforest`; Starship palette names `blueforest` (dark) and `blueforest-light`; Starship packages `blueforest-starship-preset`, `blueforest-starship-palette` and `blueforest-starship`; OpenCode theme name `blueforest`; OpenCode package `blueforest-opencode-theme`; sbt package `blueforest-sbt-prompt`; sbt theme `BlueforestTheme` from the upstream `sbt-prompt` plugin; eza package `blueforest-eza-theme`; eza theme file `blueforest.yml`, which eza reads as `theme.yml`; Zed package `blueforest-zed-theme`; Zed extension id `blueforest-theme`; Zed theme name `BlueForest - Dark`; Yazi package `blueforest-yazi-theme`; Yazi flavour name `blueforest`, the name of the directory `blueforest.yazi`; kitty package `blueforest-kitty-theme`; kitty theme file `blueforest.conf`, which kitty reads as a theme of the `themes` directory of its configuration directory, and whose light variant is `blueforest-light.conf`; MkDocs package `blueforest-mkdocs-theme`; MkDocs stylesheet file `blueforest.css`, which MkDocs reads through the `extra_css` option of its configuration; Claude Code package `blueforest-claude-code-theme`; Claude Code theme file `blueforest.json`, which Claude Code reads as a custom theme of the `themes` directory of its configuration directory, and which is selected with `custom:blueforest`; btop package `blueforest-btop-theme`; btop theme file `blueforest.theme`, which btop reads as a theme of the `themes` directory of its configuration directory, and which is selected with `color_theme = "blueforest.theme"`; lazygit package `blueforest-lazygit-theme`; lazygit theme file `blueforest.json`, which carries the theme under the `gui.theme` key of the configuration file of lazygit, `config.yml`; md-tui package `blueforest-md-tui-theme`; md-tui theme name `blueforest`, the name of the file `blueforest.json`, which md-tui reads from `$HOME/.config/mdt/themes/`; Noctalia package `blueforest-noctalia-theme`; Noctalia palette name `blueforest`, the name of the file `blueforest.json`, which Noctalia reads from `$XDG_CONFIG_HOME/noctalia/palettes/`, and which is selected with `[theme] source = "custom"` and `custom_palette = "blueforest"`. Note the lowercase `f` in `Blueforest-color-theme.json`.
- The VS Code module is defined once, in `modules/vscode/nix/modules/default.nix`, which takes the overlay of the application as an argument. The flake module imports it for `homeModules.vscode`, and the `vscode-configuration` check evaluates it again.
- The VSIX build uses `vsce package --no-dependencies`; `.vscodeignore` decides what ships. Keep dev files out and add new runtime files explicitly. `*.vsix` is git-ignored.
- `.vscode/launch.json` points at `modules/vscode`, the directory of the extension, so it runs the extension host against it. `code --extensionDevelopmentPath=$PWD/modules/vscode` does the same from a terminal, and the built extension is at `share/vscode/extensions` of the package.
- The module of an application (`modules/<app>/flake-module.nix`) is a function of the inputs of that application: the flake of the application binds them with `flake-parts-lib.importApply` and publishes the module as `flake.flakeModules.default`. The arguments of the module are the ones of the flake that imports it, so `inputs` is the input set of the consumer and the packages are built with the nixpkgs of the consumer; the checks use `appInputs`, the inputs of the application. A consumer that imports the module needs no `devshell`, `home-manager` or `nixvim` input of its own.
- `flake.homeModules` is only a declared option once the flake module of Home Manager is imported. The module of an application imports it, preferring the Home Manager of the consumer when it has one (`inputs.home-manager or appInputs.home-manager`), so that the option is declared once and never twice.
- Root aggregate modules are explicit: `flake.nix` currently composes the VS Code, Starship, OpenCode, sbt, Neovim, eza, Zed, Yazi, kitty, MkDocs, Claude Code, btop, lazygit, md-tui, and noctalia overlays in `overlays.default`, and the modules of the applications that provide one in `homeModules.default` and `nixosModules.default`. The modules of VS Code and Zed are not in the aggregates: a consumer imports them explicitly. The module of MkDocs is only a flake module, under the name `flakeModules.mkdocs`, and it is not in `flakeModules.default`, because the module of mkdocs-flake declares arguments and can only be imported once per flake; bat ships packages, an overlay, and a Home Manager module, and its package reaches the aggregate overlay through the overlay of Yazi, which carries it, sbt has no NixOS module because sbt has no system-wide configuration directory, and eza has no NixOS module either because eza reads its theme from the configuration directory of the user.
- The Zed theme lives in the `zed-blueforest-theme` extension, which is a submodule at `modules/zed/extension/`. Nix cannot fetch the contents of a submodule of a git tree, so the package reads the submodule directly and the checks of the repository run against the working tree (`path:.`). The release packages the submodule. The colours of the theme are checked against the VS Code and Neovim ones by the `zed-colours` check of the root, which lives in `tests/` because it spans applications.
- The theme of Zed has a variant per mode, and the extension carries them in the same file, so the `zed-colours` check compares every variant with the variants of the same mode of the other ports. The theme of Zed has no foreground for the status bar, so the status bar of the light variant is a light surface and not the dark green of the dark one.
- The Yazi theme is a flavour: the directory `modules/yazi/themes/blueforest.yazi/`, with `flavor.toml`. Yazi reads the flavours from the `flavors` directory of its configuration directory, and the theme of the user selects the flavour with the `flavor` section of `theme.toml`. The module selects it through `programs.yazi.theme` with `lib.mkDefault`, so a consumer that sets that option keeps their own theme and selects the flavour by hand. The colours of the code preview are the ones of the theme of bat: the application of Yazi takes the application of bat as an input, the flavour links to the TextMate theme of bat, and the `yazi-tmtheme` check of the root checks that the link points to the theme of bat.
- The package of Yazi carries a flavour per mode, and the module installs both of them and selects the one that matches the mode of Yazi. Every flavour links to the variant of the theme of bat that matches it, so the preview of the light flavour is painted with the light theme of bat.
- Yazi applies a flavour when the terminal answers its query about the background colour, and it does not apply it before that. The `yazi-render` check answers the query the way a terminal would, through the standard input of the pseudo terminal `script` allocates, or the flavour would never be painted.
- The kitty theme is a configuration file of kitty, and kitty selects a theme with an `include` line, not with an option. The module writes the theme to `~/.config/kitty/themes/blueforest.conf` and adds `include themes/blueforest.conf` to the configuration of kitty with `lib.mkOrder 505`, which is before every order Home Manager uses (510 and up), so that the colours of the consumer win over the colours of the theme. The `include` is relative to the directory of the file that includes it, and Home Manager links the configuration of kitty into the configuration directory of the user, so the theme is found next to it.
- The kitty theme has a variant per mode, and the switch of the variant, `blueforest-theme.kitty.variant`, selects the one that is installed: the dark one is `blueforest.conf` and the light one is `blueforest-light.conf`, and the `include` line names the file of the variant. The package carries both of them.
- kitty ignores a configuration key it does not know, and a colour it cannot resolve, and it does so silently. The `kitty-parse` check therefore parses the theme with kitty itself, through `kitty +runpy`, and looks at the colours that come out of it. Every variant is parsed on its own.
- The btop theme is a theme file of btop, and btop reads the themes of the user from the `themes` directory of its configuration directory. It selects one with the `color_theme` setting of its configuration file, whose value is the name of the file, and the module selects it with `lib.mkDefault`, so a consumer that selects a theme of its own keeps it. There is no NixOS module: btop reads no system-wide configuration file, so there is no place where the selection would live.
- btop ignores a key it does not know, and a colour it cannot resolve, and it does so silently: it falls back to the colours it ships with. The `btop-render` check therefore runs btop itself, in the pseudo terminal `script` allocates, and looks at the colours it painted and at the errors it wrote to its log.
- btop needs a UTF-8 locale to start at all, and the sandbox of a build has none: the `btop-render` check runs btop with `LC_ALL=C.UTF-8`, or it would never paint anything.
- The comments of a theme file of btop have to start at the first column, and they cannot carry a square bracket: btop reads the file line by line, and it looks for the opening bracket of the key.
- lazygit has no theme file of its own: the theme is the `gui.theme` mapping of the configuration file of lazygit, `config.yml`. The file of the theme is JSON, and JSON is a subset of YAML, so lazygit reads it as its own format, and Nix reads it at evaluation time with `builtins.fromJSON`, which is what the Home Manager module does. The colours are set one by one, each one with `lib.mkDefault`, because the settings of lazygit are one value: a value that is set as a whole is replaced by the settings of the consumer, colours and all.
- lazygit ignores a key it does not know, and a colour it cannot resolve, and it does so silently: it falls back to the colours it ships with. The `lazygit-render` check therefore runs lazygit itself, in the pseudo terminal `script` allocates, and looks at the colours it painted.
- lazygit waits for a key that never comes, and the `lazygit-render` check sends it the one that quits it, once it has painted the interface. The colours of the theme are true colour, so the check runs lazygit with `COLORTERM=truecolor`.
- lazygit renders the diffs with git, so the colours of the diffs are the ones of git and not the ones of the theme.
- The colours of the theme of lazygit are checked against the VS Code and Neovim ones by the `lazygit-colours` check of the root, which lives in `tests/` because it spans applications.
- The theme of md-tui is a palette of md-tui, the format the chooser of its themes saves: a JSON document with the colours of the interface, the colours of the headings, and the colours of the syntax. md-tui reads a palette as a whole, and it ignores one that does not carry every colour it knows, silently, so the palette of the repository carries all of them.
- md-tui reads the configuration directory of the user from `$HOME/.config`, and it ignores `XDG_CONFIG_HOME`: the module writes the palette and the selection of it with `home.file`, and not with `xdg.configFile`.
- md-tui selects a palette with the `selected-theme` file of its configuration directory, whose value is the name of the palette, and the file is written by the module with `lib.mkDefault`, so a consumer that selects a palette of its own keeps it.
- Home Manager has no module for md-tui, so the switch of the module of the application is `blueforest-theme.md-tui.enable`, and not `programs.md-tui.enable`: two declarations of the same option fail, so the option of the module would clash with the one of Home Manager if it ever gained one.
- The colours of the theme of md-tui are checked against the VS Code, Neovim and kitty ones by the `md-tui-colours` check of the root, which lives in `tests/` because it spans applications.
- The theme of Noctalia is a palette of Noctalia v5, the format of its community palettes: a `dark` object with the sixteen roles of the interface under their `m`-prefixed names (`mPrimary`, `mOnPrimary`, `mSurfaceVariant`, `mHover`, ...) and a `terminal` object with the sixteen ANSI colours, the foreground, the background, the cursor and the selection. The `terminal` block is not optional: Noctalia rejects a palette that does not carry it, and it does so silently.
- The `m`-prefixed spelling is the one Noctalia 5.4 (the version of the pinned nixpkgs) and the community palette registry use. A future Noctalia may read only the unprefixed format, which is the reason the `noctalia-render` check pins the palette against the Noctalia of nixpkgs.
- Noctalia reads the palettes of the user from the `palettes` directory of its configuration directory, and it selects one of them with the `theme.source` and `theme.custom_palette` settings. The module writes the palette through `programs.noctalia.customPalettes`, which is the option that knows where Noctalia reads it from.
- `programs.noctalia.settings` is one opaque value, so the module cannot merge the selection into it. The selection lives in `~/.config/noctalia/blueforest.toml`, which Noctalia merges with the rest of the `*.toml` files of its configuration directory, sorted by name: `blueforest.toml` sorts before `config.toml`, so a setting of the consumer wins.
- Noctalia writes the settings that the shell changes at runtime to `~/.local/state/noctalia/settings.toml`, which overrides every configuration file. Changing the theme from the shell therefore wins over the selection of the module; the documentation says so.
- Noctalia is Linux-only, so the `noctalia-render` and `noctalia-module` checks are declared with `lib.optionalAttrs pkgs.stdenv.hostPlatform.isLinux`. The `noctalia-theme` check runs on every system.
- The palette of Noctalia carries a dark variant and a light variant, and the light one is a palette of its own, not a copy of the dark one. Every pair of a role and of its counterpart clears a contrast ratio of 3.0, and the `noctalia-palette-v2` check asserts it. The palette of the format 1 is the canonical one, and the file of the format 2 is generated from it.
- A palette without the `terminal` object is rejected by Noctalia, and the shell falls back to the palette it ships with. A role of the interface or a colour of the terminal that is missing or malformed is painted as transparent black instead, so the `noctalia-render` check asserts every role and every terminal colour of the palette.
- The colours of the theme of Noctalia are checked against the VS Code, Neovim and kitty ones by the `noctalia-colours` check of the root, which lives in `tests/` because it spans applications.
- The MkDocs module is the exception to the shape of the other modules: it is a helper, not a theme of an application. It imports the module of mkdocs-flake, which declares the `documentation` options, and it appends its hook to `documentation.mkdocs-preBuildHook` with `lib.mkAfter`, so that the hook of the consumer runs first.
- The options of the module of MkDocs are `blueforest-theme.mkdocs.enable`, `blueforest-theme.mkdocs.docsDir`, `blueforest-theme.mkdocs.path` and `blueforest-theme.mkdocs.preBuildHook`. Its `enable` is on by default, so it is declared with `lib.mkEnableOption` and the default is overridden with `// { default = true; }`.
- mkdocs-flake declares `_module.args.mkdocs-flake`, so its module can only be imported once per flake. The root flake therefore does not import it: the module of the MkDocs application does, and the root imports the module of the application.
- MkDocs copies the `extra_css` files of a site from the directory of its sources, and only the files that are inside it. The stylesheet therefore has to be at `<docs_dir>/<path>`, and the hook of the module installs it there.
- The hook of the MkDocs module runs in the build directory of mkdocs-flake, where the sources of the site are copies with the permissions they have in the store. The store is read-only, so the hook makes the sources writable before it writes the stylesheet.
- The documentation site of the repository carries the theme of the MkDocs application: `docs/assets/stylesheets/blueforest.css` is a symlink to `modules/mkdocs/themes/blueforest.css`, so that the site of the working tree (`nix run .#watch-documentation`) and the site that Nix builds look the same.
- The stylesheet of MkDocs has a set of variables per mode: the dark scheme of Material and the light one. The rules of the theme are the same in both of them, and they read the colours from the variables of the mode they are in, so the colours that Material does not have a variable for are named by the theme itself, with the `--blueforest-` prefix.
- The palettes of the documentation are shown with swatches, and the stylesheet of the swatches is `docs/assets/stylesheets/palettes.css`, which the site loads through the `extra_css` of `mkdocs.yml`. It is a stylesheet of the site and not of the theme: the theme is published, and a rule of the documentation does not belong in it.
- A swatch is a `<span>` of the class `blueforest-swatch` with the colour of the swatch in its `background-color`, and it sits after the hexadecimal value of the colour. The `palette-swatches` check of the root reads the swatches of `docs/index.md` and compares them with the palette of Noctalia, so that the documentation cannot drift away from the palette.
- The themes have a variant per mode: a dark one and a light one. The light variant of a theme is named after the dark one, with `Light` appended: `BlueForestLight` in VS Code, `blueforest-light` in Neovim, Yazi, Claude Code, kitty, md-tui and Starship, and `BlueForest - Light` in Zed, which names its themes that way already. The light variant of OpenCode is not a theme of its own: the format of OpenCode carries a `light` object and a `dark` object in the same file.
- The themes of bat, of Claude Code, of kitty and of md-tui select the variant with an option of their own, `blueforest-theme.<app>.variant`, and it is `dark` by default. The option is the one of the theme, and the themes of the other applications have no variant switch: OpenCode follows the terminal, and Yazi selects both flavours at once. The palette of Starship has its own, `blueforest-theme.starship.palette.variant`, because it lives under the switch of the palette.
- The Starship preset and its palettes are installed apart: the preset names the keys of a palette and carries no colour, and the palette is what gives them one. `blueforest-theme.starship.palette.enable` defines the palette of the variant in `programs.starship.settings.palettes` and selects it with `programs.starship.settings.palette`, both with `lib.mkDefault`, so a consumer that brings a colour or a selection of its own keeps it. `blueforest-theme.starship.preset.enable` installs the wrapper package and does not select the preset either. The `starship-preset` check asserts that the preset carries no literal colour, that every key it names resolves in both palettes, and that the palettes carry the keys of the community catalogue of Noctalia for Starship, the `starship-palette` check compares the packaged palettes with the sources, and the `starship-render` check renders the preset with each palette and with the palettes of the community catalogue.
- The names of the keys of the palettes of Starship are the ones of the palette of the community catalogue of Noctalia for Starship, so that the preset of the repository paints with the palette of Noctalia as well. The catalogue writes the palette into the configuration of Starship and selects it, and the preset names nine of its keys: `blue` (primary), `base` (on primary), `text` (secondary), `peach` (tertiary), `flamingo` (error), `green` (success), `mantle` (surface), `surface1` (surface variant) and `crust` (hover). The rest of the keys carry the colours of the terminal of BlueForest. The check of the preset holds the list of the keys of the catalogue, so that the two cannot drift, and the check of the render holds the palettes of the catalogue in `modules/starship/tests/`, so that the preset is proved to paint with them.
- The preset of Starship can be enabled with a template of the community catalogue of Noctalia for Starship: the template writes the palette and the preset names the keys of it. The palette of the repository cannot, because the template and the module write the same configuration of Starship. The template writes the configuration file of Starship, so it needs one it can write: a configuration that Home Manager manages is a link into the store, and the store is read-only.
- The prompt of Starship is two lines: the information line, and the line of the character. The duration of the last command and the Nix shell are at the right of the information line, and they are a `fill` segment of the format and not a `right_format`: a right prompt is a prompt the shell renders on its own, zsh places it at the right of the last line, and bash has none at all. The fill symbol is a space, and its style is empty, so the padding it writes is invisible.
- A theme of OpenCode has a mode per appearance, and every mode is checked on its own: the modes do not inherit from each other, so a reference that resolves in one of them may not resolve in the other. The `shape.nix` and `references.nix` libraries of the checks of OpenCode take the mode into account, and the check of the theme runs over every mode.
- The roles of a theme of OpenCode are the roles of the other ports: the comment is the comment, the keyword is the keyword, and the string is the string, so that a token is painted the same everywhere. The `roles.nix` library of the checks of OpenCode resolves the references of the theme and gives the colour of every role of every mode, and the `opencode-roles` check compares them with the ones the other ports use.
- The theme of OpenCode is a system of ramps of its own: the nine steps of a hue are shades around the colours of the palette, and they are not colours of the palette. The `light-colours` check of the root therefore skips the ramps and compares the colours a theme names outside of them, which are the ones of the palette.
- The light palette of Noctalia is the reference of the light themes: every colour of a light theme has to be one of the colours of the light palette, and the `light-colours` check of the root asserts it. The amber of the library is the one exception, and the check names it: it is the amber of BlueForest, and it is the same in both variants of the syntax palette.
- The light theme of VS Code is the reference of the light themes, the way the dark theme is the reference of the dark ones: the check of the colours of Noctalia compares the variants of the palette with the themes of the same mode, and the light half waits for the light themes of the other applications.
- Every render check covers the light variant as well, and not only the dark one: a theme that paints the dark variant well and the light one badly is a theme that is broken. The check of Yazi asks the terminal for its colour scheme, because Yazi picks the flavour of the mode the terminal reports, and it renders the file twice: once with a terminal that reports a dark scheme, and once with a terminal that reports a light one.
- The Neovim package is a plugin (`vimUtils.buildVimPlugin`), so that the colourscheme is at `colors/blueforest.lua` and the theme of lualine at `lua/lualine/themes/blueforest.lua`, which are the two places Neovim and lualine read them from. The plugin directory of the runtimepath is named after the `pname`, not after the store path of the derivation. The package carries a variant per mode, so the colourscheme of the light one is at `colors/blueforest-light.lua` and the theme of lualine at `lua/lualine/themes/blueforest-light.lua`.
- The colourscheme of Neovim is one file with a palette and the groups that read it, so the light variant is the same file with another palette, another name and another mode of the editor. The check of the theme reads both of them with the probe, and lualine caches the theme it looks up by the name of the colourscheme, so the probe drops the cache before it looks the light one up.
- The Neovim module adds the theme to `programs.neovim.plugins` with `lib.mkDefault`, and does not select the colourscheme: Home Manager drops `extraConfig` when the consumer sets `initLua`, so the selection belongs to the consumer's own configuration (`vim.cmd.colorscheme("blueforest")`).
- The nixvim module (`modules/neovim/nix/nixvim.nix`) is imported *into* the configuration of nixvim (`programs.nixvim.imports`), not into the configuration of the system: nixvim builds an instance of nixpkgs of its own, so it has to add the overlay of the theme itself. It only uses three option names of nixvim (`nixpkgs.overlays`, `extraPlugins`, `colorscheme`), so it does not depend on the version of nixvim; only the check does.
- lualine finds the theme of the statusline on its own: its `auto` theme looks the theme up by the name of the colourscheme, and both are `blueforest`. Only the sections of the statusline are configuration.
- The theme of Neovim defines the seven `RainbowDelimiter*` groups, because the rainbow-delimiters plugin reads their colours from the colourscheme. A group the theme does not define leaves the rainbow without a colour.
- The OpenCode module needs `programs.opencode.cli`, which Home Manager gained in commit `6d9655f764`; the `home-manager` input of the root flake is pinned to a revision that has it.
- The OpenCode module does not enable OpenCode: Home Manager writes the theme and the settings of the terminal only when the program is enabled, so the consumer decides.
- Every theme of the repository has a switch of its own, `blueforest-theme.<app>.enable`, and it is off by default. The switch is separate from `programs.<app>.enable`, so that the theme and a template of the community catalogue of Noctalia are alternatives, and so that a configuration that wants the theme of one application only does not get the themes of all of them. The switch does not apply to VS Code, to Zed, and to MkDocs: they are installed as a package, as an extension, and as a stylesheet. The options of the repository live under `blueforest-theme`, and not under `blueforest`, so that they do not collide with the options of a consumer.
- The module of an application writes its theme under `lib.mkIf (config.blueforest-theme.<app>.enable && config.programs.<app>.enable)`, and the assertions of the module live outside of that condition, so that a configuration that asks for the theme and enables a conflicting template fails to evaluate.
- The templates of the community catalogue of Noctalia write the configuration of the applications they theme, so a theme of the repository and a template of Noctalia cannot be enabled at the same time. The applications with a template are bat, btop, Claude Code, kitty, OpenCode, and Starship. The assertion of the module reads the ids of the templates from `programs.noctalia.settings.theme.templates`, and it degrades to an empty set when the settings of Noctalia are a string or a path, because the configuration of Noctalia is one opaque value. Starship is the exception: the preset of the repository is a package and does not write the configuration, so only the palette of the repository conflicts with the template.
- The assertion of the conflict is inlined in the module of every application that has one: the applications are flakes of their own, and a relative import that leaves the directory of an application cannot be fetched by Nix. The check of every application proves that the assertion fires, with `builtins.tryEval` over a configuration that enables both.
- Home Manager's `programs.opencode.themes` only takes a path, never a store path string: give it a path literal, or the theme is taken for a JSON object and regenerated.
- OpenCode ignores a theme it cannot read, and it ignores it silently: a missing token or a colour that does not resolve makes it fall back to the theme it ships with. The checks of the application stand in for it, because a TUI cannot be rendered in a build.
- The root `overlays.default` composes with `lib.composeManyExtensions`, not by hand: an overlay takes `final` and `prev`, and folding them by hand loses one of the two. `tests/overlay.nix` guards the result.
- The workflows are rendered by `actions-nix`, whose module is imported into the root flake. `flake.actions-nix.workflows` is a top-level option, not a per-system one: `perSystem.<system>.flake` is not an option. Render with `nix run .#render-workflows`, and commit the result; the pre-commit hook of the development shell does it for you.
- The rendered files carry the header that `actions-nix` writes, and PyYAML folds the long expressions at eighty columns: the value of a folded scalar is the same, but the file reads differently from a hand-written one.
- An expression of GitHub is written `\${{ ... }}` in a double-quoted string of Nix, and `''${{ ... }}` in an indented one. The second is easy to miss, and the file does not evaluate without it.
- `actionlint` is part of the check of the workflows, and it is strict: the inputs of a reusable workflow go under `on.workflow_call.inputs`, a job that reads the output of another job uses `needs.<job>.outputs.<name>` and not `steps.<id>.outputs.<name>`, and the `schedule` trigger takes a mapping (`{ cron = "..."; }`) and not a bare string.
- An explicit `if` on a job replaces the implicit one, which skips the job when a job it needs did not succeed. Every job of the release workflow that carries a condition therefore states the result of the jobs it needs. The release workflow has no condition on the applications: a tag releases all of them.
- The CI workflow has a `merge-gate` job, which depends on the `checks` job and is the required status check of the repository. It carries `if = "always()"`, so that GitHub always has a status to report, and it states the result of the checks it needs: a required check that is never reported leaves the pull request waiting forever.
- `RENOVATE_ALLOWED_COMMANDS` is a global option of Renovate, so it comes from the environment and not from `renovate.json5`. The hosted application does not run commands at all, so the option is not used here.
- The READMEs are short entry points, not installation manuals: the root `README.md` links to the doc site, and every `modules/<app>/README.md` links to its page under `docs/themes/`. Do not put installation steps, output tables, or repository structure back into them.
- The docs use `mkdocs-material` with `font: false`, so the build stays hermetic. Do not add a plugin that downloads assets at build time. Links from `docs/` to repository files outside `docs/` use absolute GitHub URLs, not relative paths, because `mkdocs build --strict` validates internal links.
- The code blocks of the documentation are marked with a language the applications of the repository know, and the shell blocks are marked `bash`. The marker decides whether every application highlights the block or leaves it alone: `console`, for instance, is an alias of the session lexer of Pygments and of the session grammar of Shiki, and nothing else knows it, so a block marked with it comes out plain in the site and in every editor but those two. The `fences` check of the root fails when a block carries a marker the applications do not know.
- The shell tokens are painted with the same colours in every application of the repository: the command is a function (#a2cff5), the arguments are parameters (#e7e7e7), the options and the operators are operators (#ffcc33), the punctuation is punctuation (#e7e7e7), the strings are strings (#80ff80), the variables are variables (#fffab1), the numbers are numbers (#ff8080) and the comments are comments (#a0ffa0). The checks of the applications assert it: the `vscode-theme` check of VS Code, the `bat-render` check of bat, the shell groups of the theme check of Neovim, the `zed-colours` check of the root and the `mkdocs-render` check of MkDocs.
- The documentation site deploys to GitHub Pages from the `docs` workflow. Do not add a second deployment workflow: the release calls the same one.
- The sbt prompt is not defined here: `modules/sbt/config/` only declares `com.github.alonsodomin:sbt-prompt` and selects `BlueforestTheme`. Keep it that way; the prompt and the palette live upstream at <https://github.com/alonsodomin/sbt-prompt>.
- sbt has nothing to publish but its two files: the prompt and its theme are provided by the upstream plugin, so the release of the repository carries them as an asset of their own, in `workflows/release.nix`.
- The sbt Home Manager module is optionless and inert unless `programs.sbt.enable = true`. It writes `~/.sbt/1.0/plugins/sbt-prompt.sbt`, `~/.sbt/1.0/blueforest-prompt.sbt`, `$XDG_CONFIG_HOME/sbt/2/plugins/sbt-prompt.sbt`, and `$XDG_CONFIG_HOME/sbt/2/blueforest-prompt.sbt`. `home.packages = [ pkgs.blueforest-sbt-prompt ]` alone does not install them.
- sbt 1 reads its global base from `~/.sbt/1.0`; sbt 2 uses `$XDG_CONFIG_HOME/sbt/2`. In both, `plugins/` holds plugin declarations and the base itself holds the settings that can use them.

## Adding an application
Mirror `modules/bat` (the simplest app) or `modules/starship` (a package with an overlay and modules): create `flake.nix`, `flake-module.nix`, `CHANGELOG.md`, and the theme. Then register it in root `flake.nix` (path input with `follows` + `inputs.<app>.flakeModule`), expose it in the root aggregate modules if it provides one, add it to the list of applications in `workflows/lib.nix` (the CI matrix), to the table of `workflows/assets.nix` (the files of the theme and the way it is packaged), and to the packages of the monorepo in `cog.toml` (the path of the application and the path of its changelog), and update `README.md` and `NOTICE.md`. Add a user-facing page under `docs/themes/`, a nav entry in `mkdocs.yml`, and a row in `docs/themes/index.md` and the root `README.md`. Keep installation snippets in that page in sync with the configuration checks. There is no development shell per application: the tools of an application go into the `devshell.toml` of the root. The changelog of the application is a file of the repository, in the format CoCoGitto writes, and CoCoGitto fills it with the commits that touch the application.
